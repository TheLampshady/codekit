# Spec Archive, ADRs, and a Generated Product Map — Research

**Written:** 2026-10-17
**Last updated:** 2026-10-17
**Original request:** What artifacts to keep after SpecKit work and where to store them, so that devs keep decision history (complexity, architecture choices) and non-technical PMs get an accurate, askable picture of the app and can create tickets, given that the code is on GitHub with few seats and the team already uses Linear. Revised to cover what other reference docs (data models, API contracts, diagrams, glossary) industry leads recommend keeping, then again for a $0 budget, a lighter-weight alternative to a post-merge CI job, and where `/speckit.converge` fits, to move the Product Map and Glossary into Linear, updated by a GitHub Action, and to define what a good product map is, then to keep specs out of the repo entirely, with the Linear issue as their record and a Decision Log extracted after merge. Last revised to test the user's claim about which parts of a spec keep value after development, and why.
**Provenance:** Sourced claims cite primary sources inline; everything under Hypotheses is unmeasured. This doc stands alone.

## Summary

### Goal

Pick the post-merge artifacts (what's kept, what's thrown away, where each one lives) so engineers keep the "why" behind architecture choices and PMs can ask about the app and file tickets without GitHub seats or new spend. For a mostly single-repo setup that sometimes spans two.

## Key findings

- <a id="f-speckit-lifecycle"></a>**Spec Kit leaves artifact lifecycle to the team, and its "living spec" model risks losing rationale** ([Spec Kit: Spec Persistence Models](https://github.github.com/spec-kit/concepts/spec-persistence.html)): Spec Kit names three models: *flow-back* (all artifacts stay editable; risk is "silent divergence"), *flow-forward* (completed feature dirs are "treated as immutable"; risk is fragmented context), and *living spec* (`spec.md` is the contract, and plan/tasks are "disposable derivations rather than permanent sources of truth"; risk is "losing useful implementation rationale if derived artifacts are discarded"). The page calls the choice "a team convention, not a CLI setting." Spec Kit has no archive command.
- <a id="f-openspec-archive"></a>**OpenSpec keeps "how it behaves today" separate from in-flight changes, and archiving merges one into the other** ([OpenSpec glossary](https://openspec.dev/docs/glossary)): `openspec/specs/<capability>/spec.md` describes "how one capability behaves today"; a change is a folder under `openspec/changes/<name>/` with delta specs (`ADDED`/`MODIFIED`/`REMOVED`/`RENAMED`). Archive means "merge its deltas into the main specs and move its folder to `openspec/changes/archive/`." The archive keeps every planning artifact. Nothing is distilled.
- <a id="f-speckit-archive-ext"></a>**SpecKit's community `archive` extension folds a merged feature into a consolidated project spec, keeps the feature folder, and is meant to run after merge** ([stn1slv/spec-kit-archive v1.4.0](https://github.com/stn1slv/spec-kit-archive)): `/speckit.archive.run <feature-dir>` "consolidates finalized feature specifications, plans, and technical debt into the project's canonical memory (`.specify/memory/`)" (`spec.md`, `plan.md`, `changelog.md`, and the agent context file). It adds `[Source: specs/007-invoice/spec.md -> FR-012]` references, so the feature folder stays as the source. It confirms supersessions before deleting and asks up to five questions. Its author recommends running it "on the default branch after the feature's pull request is merged," and not in a workflow ("questions… cannot be answered") or on the feature branch ("two branches archived in parallel would each assign the same next requirement IDs and conflict at merge"). Community extensions are "discovery only" in the catalog and install with `specify extension add <id> --from <zip>` ([Spec Kit extension user guide](https://github.com/github/spec-kit/blob/main/extensions/EXTENSION-USER-GUIDE.md)). Core SpecKit loads only `constitution.md` from memory by itself. *v1.4.0 was released 2026-10-02.*
- <a id="f-adrkit"></a>**The community `adrkit` extension drafts an ADR from a SpecKit plan** ([Spec Kit community catalog](https://github.com/github/spec-kit/blob/main/extensions/catalog.community.json), [mbeacom/adrkit](https://github.com/mbeacom/adrkit)): The catalog entry reads "Pulls the decisions governing this work into agent context, checks produced plans against them, and drafts an ADR from a plan artifact" (v0.1.5). *Catalog description only; the extension itself wasn't read here.*
- <a id="f-spec-first"></a>**Most spec-driven tools, spec-kit included, are spec-first: the spec serves one change, not the feature's lifetime** ([Birgitta Böckeler, martinfowler.com, 2025-10-15](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)): She defines spec-first ("used in the AI-assisted development workflow for the task at hand"), spec-anchored ("kept even after the task is complete"), and spec-as-source. She judges spec-kit "still what I would call spec-first only," since it "creates a branch for every spec." She found its output "repetitive" and "very verbose," and wrote: "I'd rather review code than all these markdown files." A practitioner comparison describes spec-kit's "branch-per-spec workflow that causes review overload" ([Particula](https://particula.tech/blog/spec-driven-development-tools-spec-kit-vs-kiro-vs-tessl)). *Practitioner assessment, not measured.*
- <a id="f-ak-vaporization"></a>**Decision rationale that isn't recorded is lost, which makes later maintenance harder** ([Harrison, Avgeriou & Zdun, IEEE Software 2007](https://pure.rug.nl/ws/files/2815284/2007IEEESoftwHarrison.pdf); concept from Jansen & Bosch, WICSA 2005, as cited in [arXiv 1704.04798](https://arxiv.org/pdf/1704.04798)): Decisions that "exist merely as tacit knowledge in the heads of architects or other stakeholders… inevitably dissipate." As a consequence, maintainers "often fail to understand the architect's original motivation for a specific design construct." What gets lost: context, assumptions, drivers, consequences, and alternatives considered. *The Jansen & Bosch paper itself was not read; the quotes come from the citing papers.*
- <a id="f-adr-practice"></a>**In practice, ADRs help knowledge transfer, and where they're stored strongly shapes whether they're useful** ([Chalmers action research, ECSA 2024](https://research.chalmers.se/en/publication/542849); [Buchgeher et al., IEEE Access 2023](https://research.jku.at/en/publications/using-architecture-decision-records-in-open-source-projects-an-ms/)): After introducing ADRs at one company, challenges around "documentation culture, knowledge transfer" were "well addressed," and "the decision on where documentation is stored has a massive influence on its perceived usefulness." A mining study of GitHub repositories found adoption "still low," with about half of the repos that use ADRs holding only one to five. *Single-company action research plus an open-source mining study; neither measures when ADRs are read.*
- <a id="f-schema-cost"></a>**Schema changes force significant application code changes; adding or removing a table costs far more than an attribute** ([Qiu, Li & Su, FSE 2013](https://www.cs.ucdavis.edu/~su/publications/fse13-db-study.pdf); Zarras group, [via University of Ioannina](https://www.cs.uoi.gr/~zarras/papers/B8.pdf)): Across ten large open-source database applications (160K+ revisions), "schema changes induce significant code-level modifications," and some change types more than others. A second study reports about 19 code changes per table added and 59.5 per table removed, against 2 per attribute added and 3.25 per attribute removed. *Both via search summaries; the PDFs couldn't be read here.*
- <a id="f-api-breaking"></a>**API breaking changes are common and affect client applications** ([Brito et al., UFMG](https://repositorio.ufmg.br/handle/1843/JCES-ARMPK6); [ICWE 2024 OpenAPI study](https://design.inf.usi.ch/node/405)): Across 317 Java libraries, about 14.78% of API changes broke compatibility, and about 2.54% of clients were affected. Of 16,053 OpenAPI versions, only 517 APIs consistently signalled breaking changes with major versions. *Library and public-API ecosystems; no study found measures the cost to an app team changing its own API.*
- <a id="f-context-rot"></a>**Model accuracy degrades as input grows, and worse with closely related distractors** ([Chroma: Context Rot, July 2025](https://research.trychroma.com/context-rot)): Across 18 models (including Claude 4, GPT-4.1, and Gemini 2.5), performance "grows increasingly unreliable as input length grows," even on simple tasks, and topically similar distractors hurt more. A superseded decision is exactly such a distractor. *Distractor detail via secondary summaries.*
- <a id="f-context-engineering"></a>**Anthropic recommends the smallest set of high-signal tokens, loaded just in time** ([Anthropic: Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)): The goal is to "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome." It notes that "as the number of tokens in the context window increases, the model's ability to accurately recall information" decreases, and it recommends agents "maintain lightweight identifiers" and load details at runtime rather than up front.
- <a id="f-adr-format"></a>**ADRs are small, immutable decision files kept next to the code, with later decisions superseding earlier ones** ([Red Hat: Architecture decision records](https://redhat.com/en/blog/architecture-decision-records)): The format goes back to Michael Nygard's 2011 "Documenting architecture decisions" (Title, Status, Context, Decision, Consequences). Records are stored as text files in version control. An accepted record isn't edited; a changed decision gets a new record that references the old one. *Secondhand account of Nygard's post; the original article was not fetched here.*
- <a id="f-speckit-converge"></a>**`/speckit.converge` checks the code against the live spec before merge and only appends missing tasks** ([spec-kit `templates/commands/converge.md`](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)): It reads "`spec.md`, `plan.md`, and `tasks.md` as the **sole source of intent**," assesses the current code, and appends unmet work as a new `## Phase N: Convergence` section in `tasks.md` "so that implement can complete it." It "MUST run only after" implement. It's "APPEND-ONLY": it never modifies spec, plan, existing tasks, or code, and when everything is satisfied it leaves `tasks.md` "byte-for-byte unchanged." It is "**not** a diff tool… no git, no branch comparison, no history." *Read from the template in the repo, fetched 2026-10-17.*
- <a id="f-github-seats"></a>**Anyone with access to a private org repo uses a paid GitHub seat, read-only included** ([GitHub Docs: GitHub license users](https://docs.github.com/en/billing/reference/github-license-users)): On Team, "Outside collaborators on private repositories owned by your organization, excluding forks" consume a license, as do all org members. On Enterprise Cloud, internal repos count as well. The docs list no exemption for read-only permission.
- <a id="f-claude-project-github"></a>**Claude Projects' GitHub sync depends on each user's own repo access and syncs manually** ([Claude Help: Using the GitHub integration](https://support.claude.com/en/articles/10167454-using-the-github-integration)): Adding a private repo needs the user's GitHub auth (or an org-admin approval of their request), and a user who loses repo access can no longer view its contents in the project. Sync happens through a "Sync" / "Sync now" button. The article doesn't describe automatic sync. It only syncs file contents, not PRs or history.
- <a id="f-code-intelligence"></a>**Linear Code Intelligence answers code questions in Linear and can be opened to members without GitHub access** ([Linear Docs: Code Intelligence](https://linear.app/docs/code-intelligence)): It "lets Linear Agent answer questions about your codebase" (⌘/Ctrl+J). Setup is the GitHub integration with code access, then enabling it in Settings › AI & Agents. It's permission-aware by default, and admins can "Extend access to all members" so people without GitHub access can use it, scoped to all or selected repos. It's available on Business and Enterprise and "not available to guest users." The docs page says nothing about data handling. The [changelog (2026-05-14)](https://linear.app/changelog/2026-05-14-code-intelligence) describes it as public beta and free during the beta, *per a search summary of the changelog; not fetched directly.*
- <a id="f-linear-agent"></a>**Linear Agent reads workspace documents and creates issues from chat** ([Linear Docs: Linear Agent](https://linear.app/docs/linear-agent)): It works over "your existing workspace data," including "documents," and can "Create and update work like issues, projects, milestones and initiatives." It's on by default, limited to what the user can already see, and reachable in Slack and Teams. Plan coverage ("all plans include an amount of Agent usage") comes from the [launch changelog](https://linear.app/changelog/2026-03-24-introducing-linear-agent), *via search summary; not fetched directly.*
- <a id="f-linear-pricing"></a>**Linear pricing: Free has unlimited members and caps issues; Business ($16) unlocks Code Intelligence** ([Linear pricing](https://linear.app/pricing)): Free is unlimited members, 2 teams, and 250 issues. Basic is $10 and Business is $16 per user/month, billed yearly. Business adds guests, Linear Asks, and Code Intelligence. Whether Free includes API access isn't legible on the page.
- <a id="f-linear-free"></a>**Linear Free includes Linear Agent, and its 250-issue cap excludes archived issues** ([Linear pricing](https://linear.app/pricing)): The Free column lists "Agent platform" and "Linear Agent." The cap row reads "Issues (excluding Archive)": 250. Third-party guides say new issue creation is blocked at the cap until you archive or upgrade. *That last detail is secondary.*
- <a id="f-github-free-org"></a>**GitHub Free for organizations allows unlimited collaborators on private repos, with fewer features** ([GitHub Docs: GitHub's plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)): Free orgs get "unlimited collaborators on unlimited private repositories with a limited feature set." The paid Team plan adds protected branches, required reviewers, and more on private repos. *Read via search summary of the current docs page; the feature list differs between doc versions.*
- <a id="f-deepwiki"></a>**DeepWiki generates a steerable repo wiki, but it's a separate tool and its summaries can be wrong at the edges** ([Devin Docs: DeepWiki](https://docs.devin.ai/work-with-devin/deepwiki)): Wikis are generated when repos are connected to Devin, and a `.devin/wiki.json` (`repo_notes`, `pages`) replaces the default page planning with exactly the pages you list. Higher effort levels need a subscription or credits. A [2026 third-party guide](https://mcp.directory/blog/deepwiki-mcp-complete-guide-2026) says summaries "can be wrong on the edges" and the index lags commits. *That guide is a secondary source.*
- <a id="f-cca-automation"></a>**claude-code-action runs prompt-driven automation from any workflow event** ([anthropics/claude-code-action](https://github.com/anthropics/claude-code-action)): It detects "executing automation tasks with explicit prompts" alongside @claude mentions, configured through `prompt` and `claude_args` inputs. Patterns live in its [custom automations guide](https://github.com/anthropics/claude-code-action/blob/main/docs/custom-automations.md).
- <a id="f-cca-oauth"></a>**claude-code-action can run on a Claude Pro/Max subscription token and install plugins from a marketplace** ([setup](https://github.com/anthropics/claude-code-action/blob/main/docs/setup.md), [usage](https://github.com/anthropics/claude-code-action/blob/main/docs/usage.md)): It takes "Either `ANTHROPIC_API_KEY`… Or `CLAUDE_CODE_OAUTH_TOKEN` for OAuth token authentication (Pro and Max users can generate this by running `claude setup-token` locally)." Inputs `plugin_marketplaces` ("Newline-separated list of Claude Code plugin marketplace Git URLs") and `plugins` ("Plugins are installed before Claude Code execution") load plugins into the run. The usage doc has no push-triggered example, and how slash commands in `prompt` behave in the action isn't documented there. Headless Claude Code does expand them: "User-invoked skills and custom commands work. Include `/skill-name` in the prompt string" ([headless docs](https://code.claude.com/docs/en/headless)).
- <a id="f-diff-on-merge"></a>**Updating docs from the merged diff works and costs little, but misses implied changes** ([Doc Drift Detection in CI, 2026-03-06](https://understandingdata.com/posts/doc-drift-detection-ci/)): This is Dosu's production workflow. On a merged PR it feeds the diff, `docs/`, and a code-to-docs mapping to claude-code-action, which opens a follow-up docs PR or logs why none is needed. Stated limits: "It catches what is explicit and misses what is implied"; each run "starts fresh"; it costs "roughly $0.50 to $2.00" per run. The team removed path filters because they skipped config/template changes that affected docs. *Practitioner write-up; the numbers are theirs.*
- <a id="f-reviewable-pr"></a>**Agent-written docs should land as a reviewable PR, checked by a second pass** ([Agent Patterns: Continuous Documentation](https://agentpatterns.ai/workflows/continuous-documentation/)): "The output must be a reviewable PR rather than an autonomous update." It recommends a generator–verifier split and warns that "a plausible-looking PR that aligns with the wrong mental model is worse than acknowledged drift." Other risks it names: review fatigue, churn between equivalent phrasings, and style erosion. *Practitioner pattern catalogue, not measured.*
- <a id="f-swimm-states"></a>**Code-coupled docs can be checked in CI and sorted into up to date, out of sync, and outdated** ([Swimm: benefits of code-coupled documentation](https://docs.swimm.io/new-to-swimm/benefits-of-code-coupled-documentation)): Docs reference specific snippets and paths. A CI check runs per commit. Trivial changes auto-sync, and substantial ones fail the check and are flagged for a person. *Vendor documentation.* This is the precedent for keeping "can be auto-fixed" separate from "needs a human."
- <a id="f-no-issue-pipeline"></a>**No published pipeline opens an issue when docs and code disagree; they open PRs or fail the build** *(absence claim)*: I searched for LLM doc-drift CI that files issues. Docverity fails the build, the Dosu workflow and agentpatterns.ai open PRs, and DriftGuard is a hackathon dashboard. None file tickets.
- <a id="f-cc-hooks"></a>**Claude Code hooks run shell commands on lifecycle events; prompt and agent hooks only return a decision** ([Claude Code Docs: Hooks](https://code.claude.com/docs/en/hooks)): There are five handler types. Command hooks "run a shell command." Prompt hooks "send a prompt to a Claude model for single-turn evaluation. The model returns its decision as JSON." Agent hooks "spawn a subagent that can use tools like Read, Grep, and Glob to verify conditions before returning a decision" and are "experimental." Events include `Stop`, `PostToolUse`, and `SessionEnd`. Plugins can bundle hooks in `hooks/hooks.json`.
- <a id="f-story-map"></a>**Story maps arrange a product by the user's journey: activities in order, with the tasks under each** ([Jeff Patton & Associates: Story mapping](https://jpattonassociates.com/story-mapping/)): Patton describes it as telling "the user's journey through your product by building a simple model," keeping "your users and what they're doing with your product front and center," which he finds "better than getting lost in feature arguments." The "backbone" of activities left to right, with tasks and stories beneath, comes from his 2014 book *User Story Mapping* (O'Reilly). *The backbone structure is from secondary summaries (e.g. [barkingiguana.com](https://www.barkingiguana.com/writing/user-story-mapping-seeing-the-whole)); the book wasn't consulted here.*
- <a id="f-capability-map"></a>**Capability maps name what an organization does, not how, so the names outlast process and system changes** ([LeanIX: defining business capabilities](https://www.leanix.net/en/wiki/ea/best-practices-to-define-business-capabilities), [Creately guide](https://creately.com/guides/business-capability-map/)): A capability is the "what" ("invoice a service"), and a process is the "how." Capabilities "are stable over time and independent of organizational structure," while processes change often. LeanIX's example: capability names tied to specific systems went stale after a platform change, and renaming them to the business outcome kept them valid. *Vendor and consultancy sources, consistent with each other but not independent.*
- <a id="f-no-product-map-standard"></a>**There is no published standard for a code-derived product map for PMs** *(absence claim)*: I searched for formats teams use to describe "how the product works" for non-engineers. I found story maps and capability maps (planning and architecture tools), BDD living documentation (executable specs), and vendor knowledge-base templates (Notion, Fabric), but no established format for a map generated from code.
- <a id="f-c4-levels"></a>**C4 recommends a system-context diagram for everyone and a container diagram for technical readers; deeper levels are optional and best automated** ([C4: System context](https://c4model.com/diagrams/system-context), [Container](https://c4model.com/diagrams/container), [Component](https://c4model.com/diagrams/component)): System context's intended audience is "Everybody, both technical and non-technical people," and it's "recommended for all software development teams." Container (deployable apps, services, databases) is for "Technical people" and is also recommended for all teams. Component diagrams: "only create component diagrams if you feel they add value, and consider automating their creation for long-lived documentation." The model's author argues for diagrams as text, which is version-controllable and diffable ([Simon Brown, speaker profile](https://sessionize.com/simonbrown)).
- <a id="f-arc42-sections"></a>**arc42's twelve-section template includes architecture decisions and a glossary, and supports a lean subset** ([arc42 docs](https://docs.arc42.org/home/)): The sections run from Introduction and Goals through Glossary. They include "Architecture Decisions: Important, expensive, risky or contentious decisions," "Risks and Technical Debt," and "Glossary: Definitions of important business and technical terms." It describes a lean approach for teams looking "to shorten or streamline your documentation pragmatically," while saying "there is some information about your system that you should always document." The page doesn't say which parts are the minimum.
- <a id="f-tbls"></a>**tbls generates schema docs and Mermaid ER diagrams from the database, takes business comments from config, and checks drift in CI** ([k1LoW/tbls](https://github.com/k1LoW/tbls)): `tbls doc` writes GitHub-flavoured Markdown per table, with ER diagrams in svg/png or `mermaid`. It supports PostgreSQL, MySQL, SQLite, SQL Server, BigQuery, Snowflake, MongoDB, and others, plus JSON schema files. A `comments:` block in `.tbls.yml` adds table and column descriptions without touching the database, and `lint` with `requireColumnComment` finds undocumented columns. The README says to "Check for document updates by running `tbls diff` or `tbls lint` in CI."
- <a id="f-api-first-tradeoff"></a>**Code-first API specs only work if the generated contract is real; design-first is for contracts that matter before code exists** ([Kin Lane, API Evangelist, 2026-06-29](https://apievangelist.com/2026/06/29/design-first-or-code-first-pick-and-know-the-cost/)): "A code-first program lives or dies on whether the generated contract is real." Code-first is common and acceptable for internal and legacy APIs, with governance (linting, review) run on the generated spec. He prefers design-first "for anything that matters" and recommends tightening "toward design-first discipline as an API approaches production readiness." *Practitioner opinion from a well-known API author; the article doesn't mention contract tests.*
- <a id="f-ubiquitous-language"></a>**A ubiquitous language is a precise shared vocabulary that developers and domain experts build together** ([Martin Fowler: Ubiquitous Language](https://martinfowler.com/bliki/UbiquitousLanguage.html)): It's "a common, rigorous language between developers and users," "based on the Domain Model used in the software." Domain experts "should object to terms or structures that are awkward or inadequate," developers "should watch for ambiguity or inconsistency," and "the language (and model) should evolve as the team's understanding of the domain grows."
- <a id="f-diataxis"></a>**Diátaxis separates reference (facts about the machinery) from explanation (the reasoning)** ([Canonical: Diátaxis, a new foundation](https://ubuntu.com/blog/diataxis-a-new-foundation-for-canonical-documentation)): It sorts docs into four types: tutorials, how-to guides, reference, and explanation. Reference supplies facts and "is not a place for explaining, or instructing." Each type should stay separate. *Canonical's adoption post; the framework's own site (diataxis.fr) was not fetched here.*

## How this applies to your request

**Governing rule: code in GitHub, prose in Linear.** The user's position, adopted as the design rule: GitHub is for reviewing code, and spec text doesn't belong in PRs. Specs are working files while a feature is built ([spec-first](#f-spec-first)). Their lasting content, the decisions, goes to the Decision Log, and what the system supports is regenerated from code into the Product Map.

**What to keep.** Your instinct to not archive every spec lines up with Spec Kit's own framing ([lifecycle](#f-speckit-lifecycle)): plan and tasks are derivations, and the one thing you lose by discarding them is rationale. [H1](#h1) is the bet that an ADR pulled out at merge captures that rationale and that nothing else is worth keeping. It's cheap to try, because the spec is still in git history if the bet turns out wrong. OpenSpec's model ([archive](#f-openspec-archive)) is the alternative: keep everything and also maintain a hand-curated "how it behaves today" spec. That's close to a product map, but it's written by devs in requirement language, and it's exactly the kind of doc you've seen go stale.

**Where PMs live, at $0.** The seat constraint rules out anything that reads GitHub as the PM ([seats](#f-github-seats), [Claude Projects](#f-claude-project-github)). Code Intelligence ([Code Intelligence](#f-code-intelligence)) would let PMs ask about the code directly, but it needs Linear Business. The free path is Linear Free ([Linear Free](#f-linear-free)): unlimited members, and Linear Agent ([Linear Agent](#f-linear-agent)) is included. It reads Linear documents and can turn a conversation into an issue. Without Code Intelligence, the agent only knows what's in Linear, so the documents *become* PMs' view of the code. That makes the product map, glossary, and decision log the core of the plan rather than an extra, and it raises the stakes on [H2](#h2) and [H6](#h6). The 250-issue cap counts only unarchived issues, so archiving done work keeps a small team under it. The other free route, a GitHub Free org with PMs as read-only collaborators ([GitHub Free org](#f-github-free-org)), would drop protected branches and required reviewers on private repos, and it still wouldn't give PMs a usable view of the code.

**Drift, and where the map lives.** Your instinct ("detect drift on update and use it to update the map") is what the published workflows do ([diff-on-merge](#f-diff-on-merge)). For the map itself, drift and updating are the same step, and [H3](#h3) narrows the "drift check" idea to code contradicting an accepted ADR. Keeping the map in the repo turned out to be the real friction: a generated doc nobody reviews as code still shows up in every code PR. So the Product Map and Glossary live only in the Linear project, where PMs read and edit them. That also removes the separate publish step. A Claude Code hook can't do the update ([hooks](#f-cc-hooks)): command hooks run shell, prompt and agent hooks return decisions, and none of them fire on a merge. A local git hook would fire on every developer's pull and race on the same document. A GitHub Action on each PR merged into the base branch runs once per merge on one runner, one at a time, and on a Claude Pro/Max subscription token, so it adds no API bill ([OAuth and plugins](#f-cca-oauth)). It installs codekit from the marketplace and runs the same `/project-docs` a developer can run locally. The map records the commit it was last synced to, so a skipped run is caught up by the next one. What you give up is PR review of map changes ([reviewable PR](#f-reviewable-pr)), so the verification pass carries more weight, and [H4](#h4)'s full rebuild stays available on demand.

**What survives a spec, and why.** Your claim is that spec files are pointless after development except for a few key points. The sourced support is that spec-kit is spec-first ([spec-first](#f-spec-first)) and that its own docs treat plan and tasks as disposable ([lifecycle](#f-speckit-lifecycle)). Two things survive. First, the **decisions**: the reasons, rejected options, and accepted complexity, which spec-kit already writes in `research.md` and the plan's Complexity Tracking. Losing them demonstrably hurts later maintenance ([vaporization](#f-ak-vaporization)), which supports keeping them. That they matter *only* when changing something is your position, not a finding ([H9](#h9)). Second, **what the system supports**, which isn't taken from the spec at all: the code replaces `data-model.md` and `contracts/`, so the Product Map regenerates the entity and interface view from code. Changes to the data model or an external API are measurably the expensive ones ([schema cost](#f-schema-cost), [API breaking](#f-api-breaking)), which is why that view matters for effort questions ([H10](#h10)).

| What to extract | Common name | From | Lives in | Why |
|---|---|---|---|---|
| Decisions, rejected options, accepted complexity, assumptions | Decision Log (ADRs) | `research.md`, plan's Complexity Tracking, spec's Assumptions | Linear project document | Used when changing or improving something ([H9](#h9)) |
| What the app offers | Product Map (capability map) | code | Linear project document | PMs see what exists |
| What data and APIs support | Domain model + Interfaces sections | code | inside the Product Map | Effort questions ([H10](#h10)) |
| Shared terms | Glossary (ubiquitous language) | spec's Key Entities, code | Linear project document | Same words for PMs and devs |

**What a good product map is.** Nobody has published a standard ([no standard](#f-no-product-map-standard)), so the template borrows from two hand-drawn practices: story maps arrange a product by the user's journey ([story maps](#f-story-map)), and capability maps name the outcome rather than the mechanism, so the names outlast refactors ([capability maps](#f-capability-map)). [H8](#h8) is the bet that this layout works for a generated map too. Each capability carries its own rules, screens, and code links, so a merge that touches one capability changes one entry. Entities, integrations, and known limits sit beside the activities. Updates run after every merge and change only the entries the commits touched. A full rebuild runs on demand, keeping existing names wherever the meaning didn't change.

**Where converge fits.** `/speckit.converge` ([converge](#f-speckit-converge)) points the other way from the product map. It checks the code against the *live* spec during the build and appends missing work for implement to finish. So it belongs at the end of `sdd-implement`, looping implement → converge until it reports clean, and it has to run *before* the spec is archived, because it needs `spec.md`, `plan.md`, and `tasks.md`. It doesn't help after merge: it has no git or history awareness, and once the spec folder is gone there's nothing for it to read. Order of operations: implement → converge → commit → `sdd-push` (rebase, archive into the consolidated spec, push) → merge → the `codekit-docs` Action updates the Product Map in Linear.

**Scale.** At one repo, occasionally two, one Action run per merge on a subscription token adds no API bill. Each run counts against the plan's usage. For the two-repo case, each repo would need its own document title in the shared project. How to merge them is an open question, not something the research settled.

**The other reference docs: data models, API contracts, diagrams, glossary.** Industry guidance splits cleanly by whether a tool can produce the doc from code. Data models ([tbls](#f-tbls)), API contracts for an existing service ([code-first](#f-api-first-tradeoff)), and C4's deeper diagrams ([C4](#f-c4-levels)) are all things the leads say to *generate* and check in CI. That fits your "code is the source of truth" stance, and it's the bet in [H5](#h5). What code can't hold are decisions (already the ADRs), vocabulary ([ubiquitous language](#f-ubiquitous-language), [H6](#h6)), and the one-page system context, which C4 explicitly aims at non-technical readers. arc42 ([arc42](#f-arc42-sections)) is a useful checklist, but twelve sections is more than a small team will maintain. The lean subset that matches this setup is decisions, glossary, context, and risks (the "known limits" section of the product map). SpecKit's per-feature `contracts/` folder is the design-first part: it's the agreement before code exists. After merge, the generated OpenAPI file is the truth, and `contracts/` goes with the spec folder (A2).

## Decisions (deliberately not doing)

- **Committing spec text (SpecKit and no framework).** Governing rule: code in GitHub, prose in Linear. GitHub is for reviewing code, and spec folders are build-time working files (A2).
- **A separate archive PR after each merge.** The user rejected extra PRs.
- **SpecKit's community `archive` extension.** It consolidates feature specs into `.specify/memory/`, which is spec text committed to the repo, against the governing rule that prose lives in Linear ([archive extension](#f-speckit-archive-ext)).
- **Feeding the Decision Log to `sdd-plan` or spec-kit.** The log grows with every ticket, and its entries are AI-extracted, so as planning context it would bloat and carry wrong or superseded entries ([context rot](#f-context-rot), [context engineering](#f-context-engineering)). An AI-written "decision" that steers future plans unreviewed is the generated-rationale risk. Kept as a human reference only.
- **A `.codekit/` folder in the repo.** Review reports and working copies go in the system temp folder instead, which the OS clears, so nothing is left in the codebase to manage.
- **ADR files in the repo (the earlier A1).** Decisions go to the Decision Log in Linear instead (A12), pulled from `research.md`, which spec-kit already writes in Decision / Rationale / Alternatives form.
- **Uploading tasks, contracts, and data models to the issue.** Build-time only; the code supersedes them once the feature ships.
- **Claude Projects as the PM home.** Private-repo sync needs each user's own GitHub access, and syncing is manual, so it fails the seat constraint.
- **Giving PMs GitHub read access.** Read-only outside collaborators on private repos still use a paid seat.
- **DeepWiki or Google Drive as the primary PM surface.** Each adds a tool PMs don't otherwise use. Linear already does Q&A, documents, and ticket creation in one place.
- **Linear Code Intelligence (deferred, not rejected).** It needs Business ($16/member), and the budget is $0. Revisit if H2's check shows document-only Q&A falls short.
- **Downgrading to a GitHub Free org so PMs can be collaborators.** It loses protected branches and required reviewers on private repos, and raw repo access doesn't give PMs a readable view anyway.
- **Product Map and Glossary as repo files.** Generated docs nobody reviews as code still add noise to every code PR, and PMs can't edit them. They live in the Linear project instead.
- **Updating the map inside `sdd-push` (the earlier A4).** It misses PRs made outside codekit and puts doc changes in code PRs. The post-merge Action replaced it.
- **A local git hook running headless Claude.** It fires on every developer's pull, races on the same Linear document, and needs Claude and a Linear key on every machine.
- **A Claude Code hook for doc updates.** Hooks run shell or return decisions, they don't fire on merges, and they don't run in Antigravity.
- **Using `/speckit.converge` for post-merge drift.** It needs the live spec files and has no git awareness. It belongs in the build loop (A11).
- **Auto-fix PRs for decision conflicts.** They assume the code is right. A conflict with an accepted ADR is a judgment call ([H3](#h3)).
- **Filing tickets because the map is stale.** The next regeneration fixes the map, so a ticket would just be noise ([H3](#h3)).
- **Adopting the full arc42 template.** Twelve sections is more than a small team maintains. Only decisions (ADRs), glossary, context, and risks (the map's "known limits") are kept.
- **Hand-drawn component or code-level diagrams.** C4 marks them optional and suggests automating them. They'd go stale like the specs did.
- **Hand-maintained long-lived OpenAPI or schema docs.** A tool can derive both, so a hand-written copy is a second source that drifts ([H5](#h5)). This would flip for a public or partner API, where design-first makes the contract the authority.
- **Tutorials and how-to guides (the rest of Diátaxis).** They serve onboarding and operations, not this goal.

## Open questions

- **Code Intelligence data handling and post-beta pricing.** If it's revisited, find out both first. The docs page says nothing about either.
- **`documentUpdate` input shape for project documents.** I couldn't verify it against Linear's API reference. Confirm it in the schema before building A5.
- **In-session doc updates (from retired H7).** Would updating the docs inside the PR-authoring session have caught most changes at lower cost? Nothing tests it now, since the Action replaced that design.
- **Slash commands and plugins in the Action.** The action documents `plugins` and `plugin_marketplaces` but shows no push-triggered example, and it doesn't say how it treats a slash command in `prompt` for a plugin with `disable-model-invocation`. Watch the first run. If it fails, point the prompt at `project-docs/SKILL.md` by path.
- **Linear markdown round-trips.** Linear rewrites markdown on save. Check that the Glossary table and the `Synced to commit` line survive a pull-and-push unchanged.
- **Linear document history.** Restoring an earlier version is described only by a third-party guide ([Guideflow](https://www.guideflow.com/tutorial/how-to-restore-a-document-version-in-a-project-on-linear)). Confirm it in the app, since it's the only undo for an Action edit.
- **Two-repo maps.** Should each repo's map stay a separate Linear document under one project, or should a combined map be generated? I have no position yet.
- **OpenSpec as an alternative to a generated map.** OpenSpec's `specs/` is a human-maintained "how it behaves today" ([OpenSpec archive](#f-openspec-archive)). If the team switched frameworks, would that make the generated map unnecessary, or would it go stale the way `spec.md` did? Untested here.
- **tbls needs a live database.** A8 runs tbls locally only when the developer has it configured. Otherwise the ERD is derived from migrations, which can miss what the database actually has.
- **Event and queue contracts.** If the app uses async messaging, the equivalent of OpenAPI for those interfaces wasn't researched here.
- **Linear Agent usage limits on Free.** "An amount of Agent usage" is unquantified. If PMs hit it, the fallback is reading the documents directly.
- **Whether Linear Free includes API access.** A5's publish uses the GraphQL API with a personal key. The pricing page doesn't make tier coverage legible, so check it with `linear_docs.py --check` on the workspace.
